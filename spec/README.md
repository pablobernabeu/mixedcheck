# Shared specification

This directory is the source of the artefacts that the R and Python packages share: the schema bundle, the registry sources in YAML and the compiled registry in JSON (Q7 in 02-decisions.md and M1 in 03-execution-plan.md).

- `versions.json` records the versions of the registry, the schemas and the canonicaliser as strings. Each package returns them through `spec_versions()`. The canonicaliser version names the rules on reading, profiles, serialisation and hashing in [docs/spec/conventions.md](../docs/spec/conventions.md).
- `errors.json` is the catalogue of error and warning codes that both packages report, with one range of codes for each area. [docs/spec/errors.md](../docs/spec/errors.md) describes it, and `tools/test_errors.py` checks it.
- `schemas/` holds the JSON Schema bundle (draft 2020-12). `schemas/defs.schema.json` has the shared definitions, among them identifiers, versions, hashes, keyed commitments, decimal strings, the six status fields and the two JSON profiles, which the other schemas refer to as `urn:mixedcheck:schema:defs#/$defs/<name>`. `schemas/declaration.schema.json` is the design declaration, vocabulary 0.1, described with the rules its validators enforce in code in [docs/spec/declarations.md](../docs/spec/declarations.md). `schemas/results.schema.json` is the results document, with its access log section and the internal sidecar, and `schemas/plan.schema.json` and `schemas/estimates.schema.json` are the Stream B plan and the bring-your-own estimates of the fitted-model contract, both drafts at version 0.1. [docs/spec/documents.md](../docs/spec/documents.md) describes the three with the rules their validators enforce in code. `schemas/ir.schema.json` is the canonical IR of a model, which [docs/spec/ir.md](../docs/spec/ir.md) specifies with the formula grammar the suite accepts. The rules for writing a schema of the bundle are in docs/spec/conventions.md (Schemas).
- `registry/` holds the sources of the registry of checks in YAML: one file for each check in `registry/checks/`, named after its identifier, and the privacy parameters in `registry/registry.yaml`. `schemas/registry-entry.schema.json` describes an entry and `schemas/registry.schema.json` the compiled registry, and [docs/spec/registry.md](../docs/spec/registry.md) describes both with the rules the compiler enforces in code.
- `unicode/assigned-14.0.json` lists, as ranges, the code points that Unicode 14.0 assigns. Both packages normalise and test for NFC only strings whose code points it lists, so that they agree whatever Unicode version their libraries implement ([docs/spec/conventions.md](../docs/spec/conventions.md), NFC). `tools/make_unicode_ranges.py` writes it with Python 3.11, whose Unicode Character Database is version 14.0.0.
- `compiled/registry.json` is the compiled registry in canonical form, the only form that the packages read. `tools/compile_registry.py` writes it from the sources. It needs PyYAML built with libyaml, runs from the repository and is never shipped, and `tools/test_compile_registry.py` tests it.
- `vendoring.json` lists every artefact to vendor, as a path from the repository root under spec/ or fixtures/. The parity harness ([parity/README.md](../parity/README.md)) reads every JSON file of spec/ listed there through both packages and compares their canonical bytes, and it requires the registry that both packages load to give the bytes of `compiled/registry.json`.
- `tools/test_unicode_ranges.py` checks `unicode/assigned-14.0.json`, and under Python 3.11 that it is up to date.
- `tools/test_declaration_corpus.py` checks the declaration and YAML corpora in fixtures/conformance/declarations/ and fixtures/conformance/yaml/: the format of their cases, their input files and their listing in `vendoring.json`, every canonical form and hash, the validity of the valid declarations and of those that reach the rules in code against `schemas/declaration.schema.json`, the issues of stage 3 against the structural validator of `tools/compile_registry.py`, the scalars of each declaration converted from YAML and every expected issue against `errors.json`.
- `tools/test_table_corpus.py` checks the table corpus in fixtures/conformance/tables/: the format of its cases, its input files and their listing in `vendoring.json`, the edgezoo inputs against the evidence they come from, the declarations against `schemas/declaration.schema.json`, the expected columns and samples, every expected issue against `errors.json` and that the corpus equals what fixtures/conformance/tools/make_table_corpus.py writes.
- `tools/test_formula_corpus.py` checks the formula corpus in fixtures/conformance/formulas/: the format of its cases, the declarations, every expected IR against `schemas/ir.schema.json` and its recorded hash, and every expected issue against `errors.json`.
- `tools/test_documents.py` checks that the JSON examples of [docs/spec/documents.md](../docs/spec/documents.md), a results document, its sidecar, a finding and a file of estimates, are valid under `schemas/results.schema.json` and `schemas/estimates.schema.json`, and the length and results file hash that documents.md states for the results document.
- `tools/test_canonicaliser_corpora.py` checks the corpora of the canonicaliser in fixtures/conformance/ (json/, numbers/, unicode/, hash/ and hmac/): the format of their cases, every hash, digest, NFC form, order, decimal string and number serialisation, and every expected issue against `errors.json`. Under Python 3.11 with the oracles of fixtures/conformance/tools/requirements.txt, it also checks that the corpora equal what fixtures/conformance/tools/make_canonicaliser_corpora.py writes.
- `tools/vendor.py` copies the listed artefacts into the packages and checks the copies. It uses the Python standard library only.

## Vendoring

Each artefact listed in `vendoring.json` is copied byte for byte from spec/ into r/inst/spec/ and python/src/mixedcheck/_spec/, and from fixtures/ into r/inst/fixtures/ and python/src/mixedcheck/_fixtures/. Each of these directories also holds a MANIFEST.json of the SHA-256 digests of its files, which the packages' tests compare with the installed files. Edit the sources here or in fixtures/, never the copies, and then run, from the repository root:

```bash
python3 spec/tools/compile_registry.py   # after editing spec/registry/, compile the registry first
python3 spec/tools/vendor.py sync    # write the copies and the manifests
python3 spec/tools/vendor.py check   # change nothing, and exit with status 1 on any problem
python3 -m unittest discover -s spec/tools -v   # test the scripts and the error catalogue
```

`check` names each problem: a copy that is missing, differs from its source or is a symbolic link, a listed source that is missing, a file in a vendored directory that is not listed, a missing or stale manifest, a listed name that R CMD build would leave out or R CMD check would reject and a carriage return or byte-order mark in any file under spec/. The files here are UTF-8 text with LF line endings and no byte-order mark. `.gitattributes` turns off Git's line-ending conversion for spec/, fixtures/ and the vendored directories, so that a checkout on any platform keeps the bytes that were hashed.
