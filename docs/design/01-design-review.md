# Design review

This document records the critical review that preceded the decision record (02-decisions.md) and the execution plan (03-execution-plan.md). It was produced in November 2026.

The review tested the assumptions behind the original two-stream architecture. A sceptical agent checked engine and package behaviour by running statsmodels 0.15.0 and reading the current CRAN sources of lme4 (2.1-0), glmmTMB, performance, insight and related packages. A seven-lens review then produced 152 edge cases, features and architectural points, each checked by an adversarial verifier, followed by a completeness critic (catalogue in evidence/review-catalogue.md). A final sceptical pass over this summary corrected 34 condensation errors, and the most consequential corrections were spot-checked against upstream sources. Every reference was checked online field by field, through publisher, repository and index pages because doi.org and Crossref were not reachable from the review environment.

## What the evidence changes

Stream A cannot be mirrored in Python on statsmodels alone. In statsmodels 0.15.0 (August 2026), `MixedLM` takes a single `groups` factor, and correlated random slopes are possible only for that factor. Crossed random effects require treating the whole dataset as one group with variance components. An intercepts-only model with 400 subjects, 100 items and 40,000 rows took 131 seconds with dense matrices and 60 seconds with sparse ones, with peak memory of 1.6 to 1.7 GB. `MixedLM` rejects weights and offsets, reports Wald z tests only and has no frequentist GLMM (its binomial and Poisson mixed GLMs are Bayesian, fitted by variational Bayes or Laplace/MAP, with independent random effects). Its boundary warning uses an absolute threshold of 0.01 on variance estimates, so it fired for data with an ICC of about 0.26 and fell silent when the same data were multiplied by 100. lme4's own singularity test (θ < 10⁻⁴) also changes when a random-slope covariate is rescaled. Both packages therefore need their own singularity criterion, defined as rank deficiency of the random-effects covariance, free of the units of the outcome and predictors and stated for a declared coding and centring.

Python Stream A will have a narrower scope unless another engine is supported. During 2026, two Rust-based engines with lme4-like scope appeared on PyPI, mixedlm (1.3.0) and glmm (0.8.0). The engine behind glmm also has an R binding, fastglmm, distributed through R-universe rather than CRAN (the CRAN package called glmm is unrelated). A shared engine would remove differences between engines, although not differences in how each binding builds the design. Both packages are less than a year old and appear to have a single maintainer each. Their accuracy claims are unverified. gpboost is older and fits GLMMs with crossed effects. pymer4 still requires R through rpy2 and has had no release since May 2025.

Parity has to be defined separately for each output. Deterministic data audits can match exactly once both packages share a canonical representation of the input and the registry fixes the rank and tolerance rules. Even then, exact agreement is guaranteed only for counts, level sets and ID mappings. Default level order, and so the reference level, differs between R, pandas and locales. A blank character ID becomes '' under `read.csv()`, NA under readr and NaN in pandas. Booleans are categorical in R and patsy but numeric in formulaic, with differently named columns. Even with identical inputs, a threshold flag can flip between languages when a statistic lies within floating-point tolerance of its cut-off, so the registry needs a 'near threshold' status. For Gaussian LMMs, a more reliable test than comparing coefficients one by one is to evaluate each engine's estimates under one reference objective, with the mapping between parameterisations stated and a relative tolerance. The REML log-likelihood that engines report changes with the units and coding of X, so parity tests should use the invariant error-contrast form. GLMMs have no shared objective across the two languages, because statsmodels offers no Laplace or quadrature likelihood. Matching random-number streams across languages is impractical. Simulation-based checks should therefore test the summarising code exactly on shared draws and test each simulator against shared fixture parameters, with equivalence margins set in advance and the simulation estimand (conditional or unconditional on the random effects) fixed in the registry.

Parity problems also exist within R. With a factor `f`, lme4's default expansion of `(1 + f || g)` is `(1 | g) + (0 + f | g)`, an unidentified parameterisation in which the intercept variance duplicates the unstructured block over the indicators for all levels of `f`, whereas glmmTMB translates the same formula to `diag()`. lme4 2.0-1 added `diag()`, `cs()` and `ar1()` covariance terms and recommends writing `diag()` explicitly. When X is rank-deficient, lme4 drops the later member of each exact dependency in model-matrix order (LINPACK's dqrdc2), and a pivoted QR in Python can drop a different column. Both packages should therefore parse the shared lme4-style grammar into a canonical intermediate representation. Where the engine accepts matrices (statsmodels), the package can pass matrices built from that representation. Where it takes formulas (lme4, glmmTMB and any model handed to `diagnose()`), the package should verify the engine's X and Z against the representation.

Some of the proposed features already exist. performance (0.19.0) has `check_group_variation()`, which labels each variable as within, between or both for each grouping factor, alongside `check_model()`, `check_singularity()`, `check_convergence()` and `check_collinearity()`. DHARMa provides simulated quantile residuals and, since version 0.5.0, simulates conditionally by default for most GLMMs. HLMdiag and influence.ME cover level-specific residuals and deletion diagnostics, and buildmer performs backward elimination from a maximal formula that the user supplies. The search found no R or Python package that derives the design-implied maximal random-effects structure from raw data, detects reused nested IDs or checks before fitting whether any combination of unit and cell leaves a random effect confounded with the residual. lme4's count-based check at fit time is partial. lmer stops when a term has at least as many random effects as observations, glmer only when it has more, structures split across terms escape it and lme4 2.x switches it off for the whole model once any term uses `diag()`, `cs()` or `ar1()`. glmmTMB and statsmodels have no such check.

There is also a gap in convergence assessment. Since lme4 1.1-38, derivatives are not computed, so the gradient and Hessian checks do not run, for models with at least 10,000 observations or at least 10 covariance parameters in lmer (20 parameters, fixed effects included, in glmer). Many maximal models exceed these limits. insight 1.7.0, which `performance::check_convergence()` wraps, returns FALSE with a message that convergence cannot be assessed for such fits when they are not singular, and for singular fits it returns whatever the optimiser reported. When glmer skips its derivatives, it also skips the step that prints the singular-fit message. The R package should be positioned as complementary to easystats and DHARMa, interoperating with them where they are sound, and concentrate effort on design-level auditing, identifiability, convergence triage, parity and reporting.

Stream B should return evidence about the design rather than 'a sound model specification'. Data can establish what a design identifies, but not which analysis is appropriate, and the literature disagrees about the latter (Barr et al., 2013; Bates et al., 2015; Matuschek et al., 2017). Stream B should return three things. The first is the design-implied ceiling for each grouping factor, with the number of informative groups behind each term. The second is an identifiability verdict on the user's formula, which is exact for Gaussian LMMs with unstructured or diagonal covariances and only a necessary condition for GLMMs. The third is a pre-specified reduction ladder whose stopping rule the user chooses and the report records. The ladder should drop nuisance slopes before slopes for the effects being tested, and correlations before variances once coding and centring are fixed, because zero-correlation models are not invariant to either. It should also keep the slope for the lower-level variable in any cross-level interaction for as long as possible, since omitting that slope usually makes inference on the interaction overconfident (Heisig & Schaeffer, 2019). A stopping rule based on convergence or singularity depends on the outcome, and the report should say so.

Outcome-blind operation is worth making a first-class mode, provided its limits are stated. A workable split is between checks that read no outcome (T0), checks that read the outcome only marginally or by cluster (T1) and checks that relate the outcome to predictors or to a fitted model (T2). The main GLMM threats, such as separation, overdispersion and zero inflation, are T2. In outcome-blind mode, Stream B would run the T0 checks and list the T1 and T2 checks as deferred, each with a decision rule that can be preregistered. Stream A would then log every rule that fired and report the preregistered model beside any adapted one.

The complexity guidance should rest on design quantities rather than rules of thumb such as 'at least five levels'. Several can be computed before fitting. One is the number of groups in which each term adds within-group rank. Another is the bound that a grouping factor with J levels supports at most J − 1 dimensions of random-effect covariance when its columns also appear in the fixed part, so that J ≤ q guarantees a singular optimum. A fit reported as non-singular in that situation signals non-convergence, and statsmodels returned such fits, flagged as converged, in 7 of 12 trials with J = 2 and q = 3. A third is the level-specific degrees-of-freedom budget, J − dim(span(X) ∩ span(Z_g)), with Z_g the indicator matrix of g and the dimension computed by rank. For Gaussian LMMs, the expected precision of variance components under assumed values can also be computed. Published work can inform the messages. Maas and Hox (2005) found level-2 standard errors biased with 50 or fewer groups, McNeish and Stapleton (2016) review the consequences of smaller samples, and McNeish and Wentzel (2017) compare methods for a top level that carries no research question, such as a handful of schools. One option in that situation, fixed school effects, turns every lower-level coefficient into a within-school effect. Cut-offs placed in a registry tend to be quoted as if the package endorsed them, so each threshold should carry its source and, ideally, simulation evidence of how often the check fires under a correct model and under the misspecification it targets. Those simulations are heavy enough to belong on the HPC.

Severity should not be graded by p-values. Thirty independent checks at α = .05 on a correctly specified model give a 79% chance of at least one flag, and a single sparse grouping factor can produce a singular fit, a convergence warning, a jump in Satterthwaite df, degenerate QQ plots and influence flags at once. Formal normality tests in particular should not be defaults: with large samples they flag trivial departures, and raw conditional residuals are dependent and heteroscedastic by construction. Each finding should carry two separate fields, assessability (not, weakly or adequately assessable) and consequence (consistent with the model, detectable but inconsequential or consequential for a declared estimand), with consequence computed against an alternative model fixed in the registry. A dependency graph between checks would let the report group downstream flags under their root cause. The report should never print 'assumptions were met', badges or aggregate scores, and it should always state what could not be assessed.

## Edge cases

The table lists the cases with the greatest consequences for validity or convergence. Most are absent from current tools or only partly handled.

| Case | Consequence | Suggested handling |
|---|---|---|
| Class labels '1', '2' and so on reused across schools | `(1 \| school) + (1 \| class)` merges same-labelled classes into a partly or fully crossed structure | Diagnose from the incidence pattern and require a nesting or crossing declaration. Offer `school:class` only when nesting is declared, because the data cannot prove that a repeated label is reuse rather than a genuinely shared unit |
| Between-unit predictor given a by-unit slope | The 'slope' variance only parameterises between-group heteroscedasticity. For a binary predictor it is unidentified with a correlated slope, and with an uncorrelated slope it is identified under 0/1 coding but not under ±0.5 coding. With three or more distinct values it is identified only through an assumed variance function | Exclude it from the ceiling and warn, without ever labelling the estimate a slope variance |
| One observation per unit per condition, or per subject-item pair | In Gaussian models, a subject-item intercept is confounded with the residual, as is a correlated slope or an uncorrelated one under ±0.5 coding. An uncorrelated slope under treatment coding is identified only by an arbitrary restriction. For binary outcomes, these terms are unidentified under a probit link and weakly identified under a logit link | Count observations per unit and cell before fitting, with wording specific to the family and coding |
| Two grouping factors that partition the data identically, such as one class per school | Only the sum of the two variances is identified | Compare the partitions without relying on labels, and report how many outer units carry information |
| Cluster-randomised trial modelled without the randomisation level | In a 300-replicate simulation run during the review (4 schools, 6 classes each, 20 pupils per class, randomisation by class), a school-only random intercept rejected a true null in 31.7% of replicates at a nominal 5% (Monte Carlo SE about 2.7 points), against 1.3% when class was included | Require the declared randomisation unit to carry a random effect or the inference to be clustered at that level, for example with CR2 standard errors (Pustejovsky & Tipton, 2018), and report the design df |
| Families with one or two children, and parent-child dyads | Singletons are legitimate. Within-family effects rest only on families with at least two children who differ on the predictor. A dyad random intercept cannot represent negative dependence and stops at zero, and `(0 + role \| dyad)` alongside a residual is unidentified | Report how many clusters have at least two members and within-cluster variation in each predictor. For dyads, require a role variable and a distinguishable or indistinguishable flag, and offer a marginal 2 × 2 covariance model (glmmTMB or nlme) |
| Factor levels emptied by listwise deletion | In R, the reference level changes silently if it is the level emptied, and contrasts set on the factor revert with a warning. patsy and formulaic keep the unused level as an all-zero column, so X becomes rank-deficient | Run every audit on the analysis sample and report how it differs from the raw data |
| Nested model comparisons on different rows | lme4's `anova()` checks only that row counts match | Fingerprint the analysis sample and refuse comparisons between different fingerprints |
| Separation in a binary outcome | Estimates diverge, and Wald statistics are non-monotone (the Hauck–Donner effect): beyond a point they fall towards zero as the effect grows, and at separation the standard error reflects where the optimiser stopped | Run a linear-programming check on the post-deletion fixed-effects matrix, give likelihood-ratio tests or profile intervals for flagged terms and report the share of clusters with a constant outcome, which can push the random-intercept SD to very large values |
| Conditional residuals in longitudinal data | They are negatively autocorrelated by construction, so true serial correlation can appear reversed | Compute within-unit semivariograms on marginal and conditional residuals, labelled as such |
| QQ plots of predicted random effects | Unbalance creates false heavy tails, and shrinkage hides real non-normality | Standardise each predicted effect by its marginal variance, computed by the suite as G Z′PZ G rather than taken from the engine's conditional variances, and flag clusters where that matrix is rank-deficient (Gaussian LMMs) |
| Conditional residuals in small clusters | Their variance shrinks, producing apparent heteroscedasticity between groups | Use studentised conditional residuals, with an assessability note for clusters of one or two |
| Ceiling and floor effects in child assessments | Interactions become scale-dependent and variance is compressed. In growth data, ceilings at later waves can produce a spurious negative intercept–slope correlation | Report boundary shares per wave and per cluster. Fix the alternative in advance: an item-level GLMM when item responses exist, otherwise a binomial or beta-binomial model for sum scores |
| SPSS or Stata imports with labelled values and codes such as −99 | Sentinel codes pass NA checks and become outliers or spurious levels | Read the label and missing-value metadata, and flag isolated sentinel values |
| Multiply imputed data and plausible values | Diagnostics from one imputation are not diagnostics of the pooled analysis, and single-level imputation of clustered data tends to shrink ICCs towards zero, which no post-fit check can detect | Run the audits on every imputation, summarise fit diagnostics as rates across imputations and require the imputation model to be declared, warning when it ignored clustering |

## Additional features and architecture

The most important addition is to make `diagnose(fit)` the main Stream A entry point, accepting models users have already fitted (lmerMod, lmerModLmerTest, afex mixed objects, glmmTMB and statsmodels results) instead of refitting from a formula. A refit by the package can differ from the user's model through REML or ML, the optimiser settings or the global `options('contrasts')`. Any refit needed for influence, ML comparisons or allFit-style triage should first reproduce the original objective within tolerance and stop with a 'refit mismatch' status otherwise. Each refit must also be diagnosed in its own right, because ML refits are singular more often than the REML fit the user saw, and lme4 does not check the convergence of its internal ML refits. Stream A should rerun the engine-free Stream B audits on its own analysis sample as far as the model frame allows (lme4 stores only the variables in the formula). The remaining audits would run only when the data are supplied and would otherwise be marked 'not assessable'. When a Stream B specification file is supplied, the two should be reconciled by hash.

A declared design specification would sharpen most checks. It would record the observation key, nesting and crossing, the randomisation unit, variable roles (treatment, baseline, post-treatment, outcome-derived), time variables and the focal estimands. It would be compositional, hashed and checked against the data, with inferred structure as a fallback reported with lower confidence.

For the shared registry, the proposal is to author in YAML but compiling to schema-validated JSON, vendored byte-identically into both packages. The R and Python YAML parsers disagree on some scalars (R's yaml reads y and n as booleans, and reads 1,000 and 1_000 differently from PyYAML), and both turn a version-like value such as 2026.10 into the number 2026.1. Both readers must also coerce types from the schema rather than trusting the parser. Each check would have a stable ID and version, a tier (T0, T1 or T2), an assessability rule, thresholds with sources and validation evidence, remedies (with the engine each needs, whether it changes the estimand and whether it uses the outcome) and a position in the dependency graph. Per-check documentation and an `explain(id)` function would be generated from it. Results would form one long table with a fixed schema and a status that distinguishes 'not available' and 'error' from 'pass'. Default JSON writers are unsuitable: `jsonlite::toJSON()` keeps four decimal places for most values, pandas' `to_json()` keeps ten digits, and Python's `json.dumps()` writes NaN and Infinity, which are not valid JSON. The number format and the treatment of non-finite values must therefore be fixed explicitly, and files compared by parsed value.

For reports, one logic-less HTML template (Mustache) could be shared by both languages, with formatting done beforehand in printf style so that the rendered strings can be parity-tested. Plots would be drawn natively with ggplot2 and matplotlib, but their inputs (bins, quantiles, envelopes) would be computed by shared logic and stored in the results JSON. The HTML would be self-contained and make no external requests. An optional .qmd export would read the stored results, verify their hash and print every value inline, so that manuscript numbers trace back to one stored result and never to a refit. Quarto should remain optional on CRAN, because not every check machine has the Quarto CLI. Rendering should be guarded with `requireNamespace('quarto', quietly = TRUE) && quarto::quarto_available()` (with quarto ≥ 1.5.0 in Suggests) and fall back to the HTML report. Because the target data include children's data, the report also needs a shareable mode with pseudonymised unit labels, binned plots with minimum cell counts and no file paths.

Other additions are worth considering. Contrasts and estimated marginal means could be first-class objects, defined as hypothesis matrices over canonical coefficient names, with df for each contrast. A methods paragraph could be generated strictly from the results, with mandatory elements and banned phrases such as 'assumptions were met'. A set of datasets with planted problems would serve testing, validation of the dependency graph and teaching. Python users who do not write lme4 syntax would need a structured specification builder, with normalisation of polars and nullable pandas types. Stream B could detect candidate grouping columns that the formula omits, such as raters, sessions or devices. When the declared goal is prediction, Stream A should switch to leave-cluster-out validation.

Two practical constraints bear on the design from the start. The first is licensing. lme4 is licensed GPL (≥ 2), DHARMa GPL (≥ 3), HLMdiag GPL-2 and glmmTMB AGPL-3, while the repository is MIT, so algorithms should be implemented from papers and documented behaviour rather than translated from source, with the provenance of each recorded. The second is installation weight. With lme4 in Imports, users who only want the audits still install it and its compiled dependencies. The alternatives are lme4 in Suggests, with Stream A gated by `requireNamespace()`, or separate audit and fitting packages.

On names, 'mix' on CRAN mostly signals mixture models (mixtools, mixdist, mixR and others), and 'mixdiag' also suggests MCMC mixing diagnostics. mixDiagnostics is not on CRAN, current or archived, and mixdiag is free on PyPI. lmecheck is free on both, although 'lme' evokes `nlme::lme`. R-universe and Bioconductor could not be checked at the time.

The scope is large for one maintainer, and two half-finished packages would serve users worse than one complete one. The proposed sequence is the registry, the canonical representation and the Stream B audits in both languages, with exact parity, then the fitted-model contract and Gaussian LMM diagnostics, then the reports and finally GLMMs and glmmTMB.

## Questions resolved in the decision record

The review closed with ten questions, each answered in 02-decisions.md under the same number.

1. Python engine strategy for Stream A: statsmodels alone, optional adapters for other engines, or a shared engine.
2. Model classes in the first release and the roadmap after it.
3. Stream B output (single formula, or ceiling, identifiability verdict and reduction ladder) and whether outcome-blind operation is the default.
4. Whether design declarations are required or optional, and their schema.
5. Report formats, plot types, privacy and accessibility.
6. Interoperation with easystats and DHARMa, and lme4 in Imports or Suggests.
7. Package names and repository layout.
8. Domains that drive defaults and examples, and the test corpus.
9. Simulation validation on the HPC and a paper (answered by the maintainer: yes to both, with no co-maintainers for now).
10. Minimum R and Python versions, and licence.
